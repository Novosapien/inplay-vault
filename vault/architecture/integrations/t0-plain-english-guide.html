◎The 30-second version

tZERO is the exchange. InPlay does not run a matching engine. We open a small number of permanent network connections to tZERO, speak a 1990s messaging protocol called FIX 4.2 down them, and fan the results out to a million users. Everything InPlay does in trading is one of three jobs: read prices, send orders, or manage accounts and money.

The appprices, orders, positions, P&L
The single most important thing to understand: a FIX session is a permanent, stateful, numbered conversation — not a request/response API. Every message carries a sequence number. If a number is missed, the conversation is broken until it is repaired. This is why the gateway is the hardest part of the build, and why it is a single point of failure that needs care.

Three more facts that shape every decision downstream:

  • tZERO has no market orders. Only limit orders exist (OrdType=2). Everything else — market orders, stops, iceberg orders — is either built by InPlay in the UI layer or does not exist.
  • tZERO does not encrypt FIX. The Order Entry spec states this plainly. All security comes from the network layer. This is why the VPC and the direct connect to tZERO matter.
  • tZERO holds the account, the cash, and the identity. The Account and Position spec shows tZERO owning KYC status, bank links, cash balances, buying power, deposits, and withdrawals. InPlay sends instructions and reads state back.

§2FIX in plain English

FIX is the messaging language that trading systems use to talk to each other. tZERO uses FIX 4.2, a version from 1998. It is not modern and it is not friendly, but it is universal, and it is what the exchange speaks.

A FIX message is a string of numbered fields

Every field is a number, an equals sign, and a value. The number is called a tag. Tag 55 means "symbol". Tag 44 means "price". You never see field names on the wire — only numbers. This is why every conversation about FIX is full of numbers, and why a tag reference is essential.

# A buy order for 500 Green Bay shares at $3.55, as it goes on the wire 8=FIX.4.2 9=178 35=D 49=INPLAY 56=TZERO 34=4711 52=20260911-23:15:42 11=IP20260911A0001 100=STX 55=IPTCPACK 54=1 38=500 40=2 44=3.5500 59=0 60=20260911-23:15:42 10=093 # the same thing in English FIX 4.2 · New Order Single · from INPLAY to TZERO · message no. 4711 order id IP20260911A0001 · route to STX · symbol IPTCPACK Buy · 500 shares · Limit order · at 3.5500 · good for today only

Three structural rules that never change

  • Every message has a header, a body and a trailer. The header always starts with tags 8, 9 and 35 in that exact order. The trailer is always tag 10, a checksum, last.
  • Every message is numbered (MsgSeqNum, tag 34). Both sides count. If InPlay receives message 4712 when it expected 4711, a message was lost and the gateway must repair the gap before continuing.
  • Silence is treated as failure. Both sides agree a heartbeat interval at logon (HeartBtInt, tag 108). If nothing arrives in that window, you send a Test Request and the other side must answer with a Heartbeat. No answer means the connection is dead.

The session is the unit, not the request

A FIX session is opened once and held open. It is identified by two names that tZERO assigns: SenderCompID (tag 49) and TargetCompID (tag 56). These are the login. There is no token, no API key, and no per-request authentication. Whoever holds the session is the client.

⚠ security consequence

The Order Entry spec states: "tZERO does not support encryption of FIX messages." All three market-data and order sessions set EncryptMethod=0, meaning no encryption. Order flow, account numbers and execution details cross the wire in clear text.

Every protection therefore has to come from the network: private connectivity, IP allowlisting, and the VPC. This is not a gap in the InPlay design — it is a constraint tZERO imposes. It does mean the network path is a compliance artefact, not just an infrastructure choice.

The administrative messages — the same on all sessions

Six messages exist purely to keep the conversation alive. They are identical across all three tZERO sessions and carry no trading information.

MsgTypeNameWhat it does
0Heartbeat"I am still here." Sent on a timer, or in reply to a Test Request.
ALogonOpens the session. Sets the heartbeat interval.
1Test Request"Are you still there?" Forces the other side to prove it.
2Resend Request"Send me messages 4711 to 4715 again." Repairs a sequence gap.
3Reject"That message was malformed." Session level, not a trading rejection.
4Sequence Reset"Skip ahead to message 4716." Used to fill a gap without resending.
5LogoutCloses the session politely.

Note the distinction between a Reject (MsgType 3) and an Order Reject. A Reject means the message itself was broken. An Order Reject is a normal, well-formed execution report saying the exchange declined the order. The user must never see the first one.

§3The three pipes

tZERO exposes four session types. InPlay uses three, with a fourth (Drop Copy, a read-only echo of execution reports) available and worth negotiating for. Each pipe is a separate TCP connection with its own logon, its own sequence numbers, and its own recovery rules.

Pipe 1 — IOI: the ticker

An IOI is an Indication of Interest: one line saying "someone will buy 500 of IPTCPACK at 3.55". Stack all the IOIs for a symbol and you have the order book. The IOI feed sends these for every active symbol at once.

The flow is simple. Log on, send one Market Data Request, and tZERO sends the current state of the whole market. When it has finished, it sends a heartbeat carrying the text IOI REFRESH COMPLETE — that string is the signal that the initial load is done. After that, updates stream automatically and forever. You never ask again.

Each IOI carries an IOItransType (tag 28): N for new, C for cancel, R for replace. The gateway applies these to its in-memory book. Alongside them, Market Data Snapshots (MsgType W) carry trades and the open, high, low, close and previous close for each symbol.

Pipe 2 — FIX Market Data: the detail view

This feed is per-symbol and lazy. You subscribe only when a user opens a symbol, and unsubscribe when they leave. It gives you everything the IOI feed does not:

  • Full book depth — aggregated one entry per price level per side, with NumberOfOrders (tag 346) telling you how many orders sit behind each level.
  • Incremental refreshes (MsgType X) — "the bid at 3.55 changed to size 300", rather than resending the whole book.
  • Halts and status (MsgType f) — is this symbol trading, halted, in auction, or unavailable, and why.
  • Session phase (MsgType h) — PRE, OPNX, CORE, POST, plus the three market-wide circuit breaker price thresholds.
  • Auction data — order imbalance (MDEntryType=A, with TradeCondition P for more buyers, Q for more sellers) and theoretical opening price (MDEntryType=y). Directly relevant to the IPO module.
  • Trade busts — a delete on a trade entry with DeleteReason (tag 285) of 0 (cancel/bust) or 1 (error).

A large book is split across several snapshot messages. LastFragment (tag 893) marks the final one. Do not render a partial book as if it were complete.

Pipe 3 — Order Entry: the only pipe that changes anything

The other two pipes are read-only. This one places, cancels and changes orders, and returns every execution report. Section 4 covers it in full.

⚠ spec bug worth reporting

In the IOI v1.2 spec, tag 264 MarketDepth lists exactly one valid value: "1 = Snapshot + Updates (Subscribe)". That description belongs to tag 263 SubscriptionRequestType, one row above. It has been copy-pasted into the wrong row.

In the FIX v8 spec the same tag is defined properly: 0 = Full Book, 1 = Top of Book. The IOI feed almost certainly means Top of Book, and t0.md assumes exactly that. It is an assumption, not a documented fact. Ask tZERO to confirm and to correct the PDF.

✕ explicitly not supported

The Order Entry spec marks these fields "currently not supported": HandlInst (21), ExecInst (18), MinQty (110), MaxFloor (111), IDSource (22), SecurityID (48), StopPx (99).

In product terms: no market orders, no stop orders, no stop-loss, no take-profit, no iceberg or reserve orders, and no minimum fill quantity. Everything the app offers beyond a plain limit order has to be constructed by InPlay out of limit orders. This is exactly why the synthetic market order (price-through) is InPlay's build, and why the education module has to teach limit orders properly.

A fill also carries the numbers the blotter needs: LastShares (32) and LastPx (31) for this fill, CumQty (14) and AvgPx (6) for the order so far, LeavesQty (151) for what is still working, plus ExecBroker (76), ContraBroker (375) and MatchID (9902) for clearing and reconciliation.

Why busts and corrections need their own state

One order can produce many fills. Each fill has its own ExecID (tag 17) and its own life. A bust or a correction arrives later, carrying ExecRefID (tag 19) that points back at the original ExecID. The order may already be complete. The fill is what changes.

This matters directly for the market maker's quote-bust control: a fill outside the price band can be reversed by the exchange after the fact. The app must be able to un-do a fill in the user's history and P&L, not just append a correction.

✓ closes a vault gap · reject reasons

trading.md records the open question "What happens when tZERO rejects an order?" Here is the complete answer. OrdRejReason (tag 103) has exactly seven values, and Text (tag 58) carries up to 256 characters of explanation.

CodeReasonPlain-English message to show
0Broker option"This order was declined. Please try again."
1Unknown symbol"That team isn't tradeable right now."
2Exchange closed"The market is closed. Trading opens at …"
3Order exceeds limit"This order is larger than your limit." — see §6.
4Too late to enter"The market closed before this order arrived."
5Unknown orderInternal fault. Never surface this wording.
6Duplicate orderInternal fault — a repeated ClOrdID. Never surface.

Cancel and replace rejections use a different message (MsgType 9) and a much shorter list. CxlRejReason (tag 102): 0 = too late to cancel, 1 = unknown order. In practice a user sees only one thing — "that order already filled" — which is a genuinely common race and needs a designed UI state.

⚠ product decision hiding in a protocol field

Day orders die every night. TimeInForce=0 (Day) is the default when the field is absent, and ExecType=3 Done for Day expires the unfilled portion at the close. A user who leaves a limit order on the Bears overnight will find it gone in the morning, with no action from them.

For a season-long game this is a significant behaviour. The alternative is GTC (TimeInForce=1), which needs RoutingInst=DNRI and survives across days. The vault has no decision on this either way — trading.md does not mention time-in-force at all. It needs one before launch, and the education content needs to match it.

§5Accounts, identity and money — the new spec

The Account and Position specification covers everything the other three do not: who the customer is, what tZERO knows about them, where their cash sits, and how it moves. It uses a different message style to the rest of FIX.

The pattern: request, then accept or reject

Every message in this spec is a four-letter custom type with a consistent suffix convention. Send UAAR to add an account. You get back UAARa if it was accepted, or UAARx if it was rejected, with Text (tag 58) explaining why. That a / x pattern holds for every message family in the document.

Two fields appear on all of them: ClOrdID (tag 11) identifies the request, and Account (tag 1) identifies the OMS account. Messages can also arrive unsolicited — if a back-office operator edits something at tZERO's end, InPlay receives the update with no ClOrdID. The gateway has to handle updates it did not ask for.

MessageFamilyWhat it does
UAAR / UEARAccountAdd or edit an account. Carries the initial cash, the buying power, and ~150 risk-control fields.
UDARAccountDelete an account.
UEAPIdentityEdit account PII — account type, broker status, domicile, accreditation.
UETRIdentityEdit the TIN record — the full KYC identity payload. KYC status lives here.
UABR / UEBRBankingAdd or edit a linked bank account. ACH and wire routing, Plaid token, approval state.
UBTMoneyBalance transfer — a deposit or a withdrawal.
UPTPositionsPosition transfer — move shares in or out of an account.
UEPRPositionsEdit a position directly.
UAUAccountAccount update — the running cash, buying power and P&L picture. Being retired in favour of UAARa.

tZERO holds the KYC record, not just a flag

The TIN message (UETR) carries the complete identity file: legal name, date of birth, SSN or EIN with type, citizenship and country codes, physical and mailing addresses, phone numbers, email, employment status, occupation, employer, stated investment purpose, and a trusted contact with their own full address. It also carries LegalEntityId (9390) and LargeTraderId (9391) for SEC CAIS reporting.

KycStatus (tag 9369) takes three values: 1 = Pending, 2 = Approved, 3 = Declined. This is the field that gates trading. BrkAccStat (9304) is separate — 1 = Active, 2 = Disabled — with BrkAccStatRsn (9305) for the reason.

Roles are explicit. TinRole (9315): Primary (one per account), Joint, Beneficiary, Beneficial Owner, Entity. Entity accounts carry company name, country and state of formation, formation date, and institution type. InPlay's users will be Primary individuals; the market maker will be an Entity.

✓ closes a vault open question

The vault's long-running question is "what does tZERO manage?" — still marked blocking in the 31-07 status synthesis. This spec answers a large part of it. tZERO manages: the account record, the KYC identity file and its status, linked bank accounts, cash balances, buying power, deposits, withdrawals, positions, cost basis, and realised and unrealised P&L.

That does not settle the ownership question — InPlay may still hold its own copy of much of this — but it removes the "we do not know what they store" part. The tables exist and the fields are named.

★ this is the buying-power API George was drafting

The 24-06 and 26-06 touchdowns record the problem: to let a user move funds from the referral wallet into the trading wallet, InPlay must tell tZERO the account's new buying power. The agreed interim answer was a start-of-day file. George proposed "a more elegant API mechanism" instead, Troy endorsed it, and George was drafting the proposal to tZERO.

That mechanism already exists in this specification. UEAR (Edit Account Request) carries CASHo (9255) and DTBPo (9253) and returns UEARa on acceptance. UBT (Balance Transfer) moves cash in or out with immediate effect. Either is a live FIX message on the same session, not an FTP drop.

This does not decide which one is correct — that is a question for tZERO (see §8). It does mean the "elegant API" is a choice between two documented messages, not a feature request.

Deposits and withdrawals — UBT

One message covers both. TxfrAmnt (9262) is positive for a deposit and negative for a withdrawal, and must be non-zero. BalTxfrTyp (9550) is 1 ACH, 2 domestic wire, 3 international wire. BankIDN (9501) names which linked bank account to use — an account can have many.

The asymmetry matters for the withdrawal flow. The spec is explicit: a withdrawal debits the account immediately, and is rejected if funds are not available. A deposit is not credited until the bank confirms it. Confirmation runs through ConfirmTyp (9551): 0 unconfirmed, 1 margin confirmed, 2 transfer confirmed, 3 bank confirm pending, 4 bank confirmed.

Bank linking (UABR) supports Plaid directly — ApprovedMethod (9516) and PlaidAccessTok (9517) are named fields. That is relevant to the payouts work, which the 24-07 touchdown flags as the launch blind spot.

⚠ naming trap

The same four tags have two different names in two tZERO documents. Order Entry v2.2 calls 9383 PosSIZ. Account and Position v3 calls it Qt. They are the same field carrying the same number.

t0.md and trading.md both use the Order Entry names throughout, which is correct for execution reports. Anyone reading the newer spec alongside them will see four unfamiliar names and reasonably assume they are new fields. Map by tag number, never by field name. Add both names to any internal field dictionary.

tZERO recalculates these on every fill, bust and correction. The 12-06 touchdown confirmed tZERO handles real-time P&L, and this spec is consistent with that. InPlay does not need to compute unrealised P&L — it needs to receive, store and display it.

§6The risk controls — a whole layer the vault has not used

Roughly 150 of the Account spec's fields are risk and compliance controls, set per account by whoever administers it. They are pre-trade — tZERO enforces them at the matching engine and rejects violating orders with OrdRejReason=3 (order exceeds limit). They are not advisory.

✓ closes two vault gaps

trading.md lists as open: "Any maximum order size? Any per-user position limits? Not discussed." The answer is that these are account-level settings on tZERO, and InPlay must decide the values and send them. They are not something to build.

Rate limits — the touchdown-spike control

MaxOrdRate (8935) and MaxDupOrdRate (8936) cap orders per unit time and repeated identical orders. The vault's own architecture estimates roughly 250,000 orders in two seconds at a touchdown spike, and names tZERO as the throughput bottleneck. These two fields are where that limit is actually set. They also apply to the market maker, which needs to cancel and replace quotes 5–10 times per second across every active symbol.

Price bands — the quote-bust mechanism

LmtPercCoreSes0 to 3 (8926–8929) and LmtPercPrePost0 to 3 (8930–8933) set limit-price percentage bands for core and pre/post sessions. LmtCents (8934) sets a maximum limit-price range in cents. Rmo_LmtPerc (8995) and Rmo_LmtCents (8996) switch enforcement on.

The 20-07 market-maker note records a "price band (~30% correction, TBD)" beyond which fills can be quote-busted. These fields are almost certainly how that band is configured. Confirm the mapping with tZERO before treating the 30% figure as settled.

Market-abuse controls

tZERO enforces anti-spoofing (SpoofAdvCutoff 8908, SpoofNumOrds 8909, SpoofPricePct 8910), anti-layering (LayeringLmt 8911, LayeringLmtExg 8912), and wash-trade prevention (Rmo_StopWashTrades 8985). ADV-based limits (8913–8917) gate activity against average daily volume.

Wash trades matter for the market maker. If the MM posts both sides of a book and a user's order crosses between them, or if the MM's own quotes ever cross, that can trip wash-trade detection. This needs raising explicitly.

★ the market maker is a configuration, not a build

The 20-07 session defines the market maker as "a synthetic tZERO entity (unlimited buying power, short-locate exemption)". Read against this spec, that description resolves into a specific account configuration to request from tZERO:

  • Rmo_EnforceDTBP = 0 and Rmo_ZeroBuyPower = 0 — the unlimited buying power.
  • Rmo_StopSSX = 0, with Rmo_EnabDigitalLocate or Rmo_AllowPrimeLocate = 1 — the short-locate exemption.
  • MaxOpenOrds and MaxOrdRate set high enough for two-sided quotes on every active symbol at 5–10 requotes per second.
  • Rmo_StopWashTrades — needs an explicit decision, because a two-sided quoter is the obvious false-positive case.
  • TinRole = 5 (Entity), with company formation details.

Treat this as a proposal to put to tZERO, not as settled fact. It is the concrete version of the ask that already exists in the vault as prose.

t0.md's throughput model assumes "~500 symbols · tZERO symbol universe" and derives 25,000 messages per second from it. The blockchain schema states the real universe: 164 team tokens, all prefixed IPTC, plus two currency tokens.

The estimate is therefore roughly three times too high. That is the safe direction to be wrong in, and t0.md already flags the whole figure as estimated and unconfirmed. Correct the symbol count when the file is next touched, and keep the headroom.

§8Twelve questions for tZERO

Each of these comes from a specific contradiction, ambiguity or silence in the documents. They are ordered roughly by how much they block.

  1. Is the Account and Position spec v3 (March 2026) current, and does it apply to InPlay? The filename says 20251015 and the title page says March 2026. Confirm the version, and confirm which of its message families are enabled for our account.
  2. Which mechanism should InPlay use to update buying power — UEAR or UBT? The vault's interim plan is a start-of-day file with no intraday rebalancing. Both messages appear to allow live updates. Can either run intraday, and is there a rate limit?
  3. Does tZERO calculate buying power for InPlay, or not? The 10-06 touchdown records that tZERO does not calculate buying power outside production broker mode, which drove the "InPlay synthetic broker" workstream. But DTBP (9256) and DTBPo (9253) are first-class fields with an Rmo_EnforceDTBP switch. Resolve which is true for our configuration.
  4. Confirm the market-maker account configuration. Put the flag list in §6 to tZERO directly: Rmo_EnforceDTBP, Rmo_ZeroBuyPower, Rmo_StopSSX, the locate flags, and the rate limits needed for 5–10 requotes per second.
  5. Will a two-sided market maker trip wash-trade or spoofing detection? Rmo_StopWashTrades, the spoofing controls and the layering limits all target patterns a legitimate quoter can produce. What exemption applies?
  6. How are the price bands configured, and do they map to the ~30% quote-bust correction? Specifically LmtPercCoreSes0–3, LmtPercPrePost0–3 and LmtCents. What are the defaults, and who can change them?
  7. What are MaxOrdRate and MaxDupOrdRate set to? The touchdown-spike model estimates ~250,000 orders in two seconds. Ask for the real ceiling and the behaviour when it is hit — rejection, throttling, or disconnect.
  8. Correct the IOI v1.2 MarketDepth definition. Tag 264 lists the description belonging to tag 263. Confirm the IOI feed means Top of Book (value 1), as the FIX v8 spec defines it.
  9. Resolve the deposit-confirmation value. The UBT prose says deposits are credited once "Bank confirmed (9551=3)", but the value table gives 3 = Bank confirm pending and 4 = Bank confirmed. Which value releases the funds?
  10. Is there a query interface, or is FIX the only route? All four specifications are streaming. There is no documented way to ask "what were this account's positions yesterday?" If a REST API exists, InPlay needs it. If it does not, InPlay must persist everything.
  11. How many simultaneous sessions may InPlay hold? The IOI spec says "a single client connection at a time". The other specs are silent, and the online documentation states no limits. Confirm the number per session type, and whether Drop Copy is available as a fourth.
  12. How do the tokenised currencies map to Currency=USD (tag 15)? The account, transfer and position messages carry USD only. The blockchain schema defines INPLAY_USD_TRADING and INPLAY_USD_REFERRAL. Related: does SecTyp (9388) treat team tokens as DAS (digital asset) or DES (digitally enhanced)?

The five things to remember

  1. Limit orders only. Everything else is built by InPlay on top, or does not exist.
  2. Sessions are stateful and numbered. A dropped connection is not a retry — it is a recovery procedure, and it differs per feed.
  3. tZERO owns the money and the identity. Accounts, KYC, cash, buying power, positions and P&L all live there. InPlay instructs and reads back.
  4. Trade limits are configuration, not code. Order size, position size, loss caps and rate limits are account fields InPlay must specify to tZERO.
  5. Map by tag number, never by field name. Two tZERO documents give the same four position tags different names.
