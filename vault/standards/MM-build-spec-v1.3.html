Chapter 01

Governance, Authority & Rules of Use

Purpose and Supersession §1.1

This document is the single authoritative engineering specification for Version 1 of the InPlay Market Maker used in the InPlay Trading Challenge. It defines what the Market Maker shall do — every algorithm, state machine, object, and acceptance requirement — without prescribing language, database, infrastructure, or internal architecture.

Upon InPlay approval, this document supersedes the InPlay Market Maker Specification v1 and the Engineering Closure Document v1.0 for implementation purposes. The placeholder appendices of the original Specification are void and shall not be referenced.

Conformance Standard §1.2

A requirement is sufficiently specified only when two qualified engineering teams, given the same accepted event sequence, approved configuration, authoritative inputs, and initial state, would produce identical authoritative outputs. Any implementation requiring interpretation of undefined business logic is non-conforming.

Section numbers are the stable requirement identifiers for traceability, code comments, tests, and defect reports.

Authority Hierarchy §1.4

  1. This Consolidated Build Specification
  2. Approved Configuration Dictionary values (Chapter 12)
  3. Approved Interface Control Documents (Matching Engine ICD, Sports Data ICD)
  4. Approved Change Orders and Requirement Clarifications
  5. External data-provider and venue technical specifications

A lower-priority authority never overrides a higher one. A later document does not gain authority merely by being later.

Version 1 Exclusions §1.5

Version 1 intentionally excludes: internally generated sports probabilities; machine-learning or adaptive valuation; predictive inventory optimization; discretionary pricing or trader intervention; profit-maximizing market-making logic; market-derived intrinsic valuation; production clearing, settlement, or broker-dealer books and records; and production functionality unique to tZERO or any regulated venue. The applicable venue is the InPlay Challenge matching environment.

Directives for Agentic Implementation §1.6

These directives are mandatory for all implementation work performed by or with AI agents.

  1. Never invent a business rule. If required behavior is not defined in this document or an approved authority in §1.4, it is an unresolved requirement. Halt that work item, raise a written blocking question to InPlay, and continue on unblocked work. Chapter 14 enumerates the known open items; the rule applies equally to any newly discovered gap.
  2. Trace everything. Every module, function, and test that implements a requirement shall cite its section number. The Requirements Traceability Matrix shall map every section of Chapters 2–13 to code and to Golden Tests.
  3. Decimal arithmetic is authoritative. Monetary values use decimal arithmetic with at least six decimal places intermediate; probabilities at least eight. Binary floating point shall not be authoritative. Prices round only at the step the algorithm specifies. Share quantities are whole shares.
  4. Determinism is testable, not aspirational. Build the replay harness first. Identical accepted inputs, configuration, and starting state shall reproduce byte-identical authoritative objects. Any nondeterminism (map iteration order, wall-clock reads inside calculations, uncontrolled randomness) is a defect.
  5. Configured values are never hard-coded. Every numeric default in this document is a Configuration Dictionary value (Chapter 12). Code reads configuration; it does not embed constants.
  6. Proposed defaults are buildable. Defaults marked "proposed" in Chapter 12 shall be implemented as given; final InPlay approval may change the value, not the mechanism.
  7. The processing sequence is fixed. No optimization may reorder the pipeline in §2.4 or the quote construction order in §5.1.

Architecture & Authoritative Objects

Pipeline §2.1

The Market Maker is a chain of independent deterministic engines. Each engine consumes published authoritative objects, performs exactly one business function, and publishes exactly one authoritative object. Business logic flows through published objects, never through shared mutable state. No engine modifies an object it does not own.

  • Approved Data Sources
  • Valuation Engine
  • Market State Engine
  • Quote Construction Engine
  • Venue Synchronization Engine
  • Position & Execution Engine
  • Audit Repository

Core Invariants §2.3

Reference Price independence. Reference Price never depends on position, P&L, participant orders, public prices, executed trades, spreads, pending orders, or cash balance — with exactly one bounded exception: the approved off-field allocation of §3.6, which admits counted trading volume only through capped, discrete, versioned weekly publications.

Position influence is bounded. Position affects only the Reservation Midpoint, displayed quantities, and replenishment. Never Reference Price, Market State, probabilities, or settlement value.

Single ownership. Every authoritative object has exactly one owner and exactly one authoritative definition.

No invented information. The system never estimates authoritative inputs; absent an approved fallback, it degrades or suspends (§6).

Replay is verification. Every accepted decision is reproducible from the audit trail; replay equality is the certification standard (§13.2).

Safety first. When reliable quotation cannot be guaranteed, quoting suspends.
Wrong quotes are worse than no quotes.

Deterministic Processing Sequence §2.4

Every accepted event follows this sequence, without exception or reordering:

  1. Accept
  2. Validate
  3. Immutable Input Snapshot
  4. Reference Price
  5. Market State
  6. Target Order Book
  7. Venue Synchronization
  8. Position Update
  9. Audit Record

Security Universe §2.5

Version 1 evaluates 170 securities — 32 NFL Team Companies and 138 NCAA Division I Team Companies — twenty-four hours per day. The Challenge covers regular-season games only: postseason games carry no on-field value, no expected value, and no off-field pool, and the set U in §3.1.1 contains only regular-season games. Complete recalculation of the full universe is required each sweep (§3.1.4); incremental valuation state is prohibited.

GEV(g)  =  (Pwin(g) × $5.00)  +  (Ptie(g) × $2.50)

Evaluation Cycle §3.1.4

Every evaluation creates an immutable Input Snapshot (latest accepted results, probabilities, off-field values, schedule, configuration) and recomputes RP completely from it. Every accepted live probability update triggers immediate valuation of the affected securities; the portfolio heartbeat sweep continues independently. Sweeps never overlap: an in-flight sweep completes, the missed interval is recorded, and the next sweep starts immediately with fresh snapshots.

MeasurementRequirement
Target sweep cadence2.0 seconds
Maximum normal interval2.5 seconds
Warning thresholdOne missed interval
Data Health escalationTwo consecutive missed intervals

Publication Rule §3.1.5

A new Reference Price Record is published only when Reference Price, Status, Confidence, or any input version (results, probability, off-field, schedule, configuration) changes. A new snapshot alone never triggers publication, a Quote Cycle, or venue activity. Only one valuation may commit per security at a time; an older calculation never overwrites a newer authoritative result.

Probability Validation and Normalization §3.2

Each unfinished game input carries: Game ID, Team Company ID, Probability Version, win/tie/loss probabilities, game status, provider event time, InPlay receive time, provider sequence (when available), and source ID. Each probability must satisfy 0 ≤ P ≤ 1.

Special Cases §3.2.2

Missing tie. If the provider expressly identifies the game as tie-impossible, Ptie = 0. Otherwise a missing tie probability makes the input incomplete; it shall not be inferred.

Duplicates. Matching source, Game ID, provider sequence, values, and provider event time → no new Probability Version, no valuation, recorded as duplicate.

Out of order. Older than the latest accepted provider sequence → retained for audit, never authoritative. Ordering falls back: provider sequence → provider event time → InPlay Event Sequence.

Corrections. A provider-designated correction with higher sequence that passes validation creates a new Probability Version, new snapshot, and immediate valuation.

Off-Field Value Methodology (Challenge) §3.6

Per-Game Pool §3.6.1

Every scheduled NFL and NCAA Division I game carries an off-field pool of exactly $2.50 per share, split between the two participating Team Companies pro rata by counted share volume. The two allocations always sum to exactly $2.50 (pool conservation). Games a team does not play contribute nothing to that team. Only regular-season games carry pools. When the opponent is outside the security universe (e.g., an FCS school with no Team Company), the universe team receives the full $2.50 as both its expected and realized allocation for that game — no capture-share calculation applies.

Volume Measurement Window §3.6.2

For team i in game g, the measurement window runs from the official final of team i’s prior scheduled game (or season open, for the first game) to the official final of game g. Every counted execution in a team’s security falls in exactly one window for that team. The two opponents’ windows need not align in calendar time; each team’s own window governs its side of the split.

Counted Volume §3.6.3

Counted volume is share volume — never notional — of executions in the team’s security where at least one side is a participant account, counted once per execution. Market-Maker-versus-Market-Maker executions, prevented self-trades, and IPO allocations never count. Counted volume is computed only from accepted Execution Events and is fully replayable.

Realized Off-Field Value §3.6.4

RealizedShare(i,g)  =  Vol(i,g)Vol(i,g) + Vol(j,g)
RAV(i)  +=  $2.50 × RealizedShare(i,g)

If both windows contain zero counted volume, each team realizes $1.25. Realization occurs only at the weekly publication: for the NFL, after the week’s final game (Monday Night Football) is official and final; for NCAA Division I, after the week’s final scheduled game is official and final. Each publication creates a new Off-Field Value Version, a new Input Snapshot, and an immediate valuation (§3.1.5). Between publications, RAV never changes. A published Off-Field Value Version is final: post-publication volume corrections (including trade busts) never restate it silently, and may modify it only through an approved correction creating a new version, mirroring §3.2.2 for official results.

Expected Off-Field Value — Popularity Model §3.6.5

EAV is the sum over remaining scheduled games of the pool times the team’s expected capture share, derived from a deterministic Popularity Index blending IPO demand (the only signal available at season open) into realized volume behavior (the best predictor once trading exists).

BDI(i)  =  Clamp( IPOEligibleOrderShares(i)IssuedShares(i),  0.10,  10.0 ) fixed at IPO completion
VMI(i,w)  =  CumulativeCountedVolume(i,w)LeagueMeanCumulativeCountedVolume(w) = BDI(i) while league volume is zero
λ(w)  =  min( CompletedPublications4,  1 )
PI(i,w)  =  (1 − λ) × BDI(i)  +  λ × VMI(i,w)
CaptureShare(i,g)  =  Clamp( PI(i)PI(i) + PI(j),  0.20,  0.80 ) opponent receives the complement
EAV(i)  =  Σg∈remaining  $2.50 × CaptureShare(i,g)

“Remaining” means not yet published, not “not yet played.” A completed game keeps carrying its expected capture share in EAV until its weekly publication, at which point the publication atomically removes it from the remaining set and adds its realized split to RAV in one Off-Field Value Version. Reference Price therefore never dips at a final whistle and jumps back at publication; the expected-to-realized swap is a single discrete step. For a non-universe-opponent game, the expected and realized value are both the full $2.50 (§3.6.1).

Properties: at season open λ = 0, so EAV is driven entirely by IPO demand; by the fourth publication it is fully volume-driven. Equal indices yield the neutral $1.25 per game. The clamp bounds any single game’s expected allocation to [$0.50, $2.00], capping both small-sample distortion and the payoff to manipulation. The Popularity Index and every CaptureShare are recomputed only at each weekly publication, published as a versioned Popularity Index Record, and are constant between publications. On-field performance enters RP only through probabilities and results (§3.1) — never through this model.

§3.6.6 · Bounded Reflexivity Prohibition Trading activity shall influence Reference Price only through this section: capped at $2.50 per game, computed only from counted volume as defined in §3.6.3, and applied only at weekly publications. Live, continuous, or intra-week volume shall never feed valuation. No other trading-derived input of any kind may enter the Valuation Engine. Any implementation path by which order flow reaches RP outside this section is a Critical defect.

Off-Field Ceiling §3.6.7

MaxApprovedOffFieldValue(i)  =  ScheduledGames(i) × $2.50

Per the approved schedule: an NFL team with 17 scheduled games has a $42.50 ceiling; an NCAA Division I team with 12 has $30.00. The formula follows the schedule, so schedule changes adjust the ceiling automatically through a new Schedule Version. This value feeds the MEV price boundary in §5.4 directly.

Position, Inventory & Reservation Midpoint

Net Position §4.1

NP  =  OpeningPosition + CumulativeBuys − CumulativeSells + CorporateAdjustments

One netted position per Market Maker per security. Negative NP is a simulated short. Version 1 imposes no inventory limits; inventory never prevents quoting. For reporting: LongPosition = max(NP, 0); ShortPosition = max(−NP, 0); the two are never simultaneously positive.

EventNet Position effect
Market Maker buy executionIncrease by executed quantity
Market Maker sell executionDecrease by executed quantity
Cancel / Replace / Rejection / AcknowledgementNo effect

Average Cost and P&L §4.2

Average Cost is maintained for reporting only and never affects quotation.

NewAvgCost  =  |OldPos| × OldAvgCost  +  AddedQty × ExecPrice|OldPos| + AddedQty adding in the same direction

Reducing a position: Average Cost of the remainder is unchanged. Crossing through zero: prior position fully closes; excess quantity opens a new position at the crossing execution price.

RealizedPnL  =  Qty × (ExecPrice − AvgCost) long reduced
RealizedPnL  =  Qty × (AvgCost − ExecPrice) short reduced
UnrealizedPnL  =  NP × (RP − AvgCost) if NP > 0
UnrealizedPnL  =  |NP| × (AvgCost − RP) if NP < 0
UnrealizedPnL  =  0 if NP = 0

Reference Price — never public trade price — is the authoritative measure for unrealized P&L.

Reference Float and Position Ratio §4.3

RF  =  TotalIssuedShares − TreasuryShares
PR  =  NPRF

Treasury shares are excluded because they are unavailable for ownership absent an approved corporate action. Positive PR is long; negative is short.

Pending Exposure and Effective Position §4.4

Pending Buy Exposure (PBE) and Pending Sell Exposure (PSE) are the sums of remaining quantity of Market Maker orders in states Pending Submit, Active, Pending Replace, Pending Cancel, and Unknown-until-reconciled, published by the Venue Synchronization Engine in the Venue State Record.

EP  =  NP + 0.50 × (PBE − PSE)

Effective Position is used only for displayed-quantity control (§5.7) — never for Reference Price or the Reservation Midpoint. The 50% weighting recognizes pending exposure without treating unexecuted orders as position.

Inventory Adjustment (Linear Capped Skew) §4.5

The neutral position is zero shares. The IPO allocation creates an opening long position, so a sell-side preference is expected as secondary trading begins.

IA  =  − Clamp( PR × S,  −M,  +M )
IA
Inventory Adjustment (dollars)
PR
Position Ratio (§4.3)
S
Inventory Skew Sensitivity — Version 1 default $1.00 (proposed)
M
Maximum Inventory Adjustment — Version 1 default $0.25 (proposed)

A 10% long position yields −$0.10; a 10% short yields +$0.10; the adjustment never exceeds ±$0.25. Long positions lower quotes to encourage selling; short positions raise them. IA is computed to six decimal places and is not independently tick-rounded — tick rounding occurs only after inside prices are constructed (§5.3).

Reservation Midpoint §4.6

RM  =  RP + IA

The Reservation Midpoint is internal, is never published outside the Market Maker, and must remain within the price boundaries of §5.4.

Quote Construction Engine

Mandatory Construction Order §5.1

Every Quote Cycle executes exactly this sequence:

  1. Validate authoritative inputs
  2. Determine Reference Price Status
  3. Read authoritative Net Position
  4. Calculate Position Ratio
  5. Calculate Inventory Adjustment
  6. Calculate Reservation Midpoint
  7. Select Market State spread and depth
  8. Construct unrounded inside prices
  9. Apply tick rounding
  10. Apply price boundaries
  11. Apply public-order-book interaction
  12. Construct remaining ladder levels
  13. Calculate displayed quantities
  14. Apply deterministic quantity variation
  15. Validate the complete Target Order Book
  16. Compare with the prior Target Order Book
  17. Publish a new Quote Version only when required

Inside Quotes and Tick Rounding §5.3

UnroundedBid1  =  RM − Spread2
UnroundedAsk1  =  RM + Spread2
Bid1  =  floor( UnroundedBid1T ) × T bids round down
Ask1  =  ceil( UnroundedAsk1T ) × T asks round up  ·  T = $0.01

Bids always round down; asks always round up. After rounding, Ask1 − Bid1 ≥ T must hold. If rounded prices would lock or cross: Bid stays rounded down and Ask is set to Bid1 + T, subject to the maximum price boundary.

Price Boundaries §5.4

MinimumPrice  =  $0.01
MaximumQuotePrice  =  MEV  =  MaxRemainingOnFieldValue + ROF + MaxApprovedOffFieldValue

No bid or ask may be zero or negative, and no ask may exceed MEV. Maximum Approved Off-Field Value = ScheduledGames × $2.50 per §3.6.7 (e.g., $42.50 for a 17-game NFL slate; season-open NFL MEV = $85.00 + $42.50 = $127.50 per share). Boundary compression: a level below minimum is set to minimum and lower duplicates are removed; a level above maximum is set to maximum and higher duplicates removed. If valid two-sided quoting is impossible within the boundaries, Market State becomes Suspended and no Target Order Book is published.

Public Order Book Interaction §5.5

The public book supplied to quote construction excludes all Market Maker orders, contains only acknowledged active participant orders, and identifies best participant bid and ask with book version and timestamp. Pending or unacknowledged participant orders are ignored.

PublicDeviationThreshold  =  max( $0.50,  10% × RP )

A public quote is actionable only within the threshold of Reference Price; quotes outside it are ignored for placement (they remain visible in the market).

Participant bid ≥ preliminary MM ask: raise the MM ask to at least ParticipantBid + T. If that would exceed MEV, publish no ask; bid levels may still publish.

Participant ask ≤ preliminary MM bid: lower the MM bid to at most ParticipantAsk − T. If that would fall below minimum price, publish no bid; ask levels may still publish.

No joining or chasing: when preliminary MM prices are inferior to actionable participant quotes but do not cross, the MM retains its preliminary prices. Version 1 prevents locking and crossing; it never improves to match participants.

Crossed participant book (ParticipantBid ≥ ParticipantAsk): the book is invalid for placement; Venue Status becomes Degraded or Unknown per the interface condition.

One-sided participant market: constrains only the opposing MM side; absence of a side never prevents MM quotation.

Deterministic Variation §5.7.3

Displayed quantity varies ±25% from the position-adjusted quantity using a deterministic seed. Canonical encoding: the five fields Security ID, Quote Version, Side, Ladder Level, Configuration Version, in exactly that order, as their canonical string forms (Side rendered BID or ASK; Ladder Level as an unpadded decimal integer), joined with a single pipe character (|), encoded UTF-8, hashed with SHA-256; the first eight bytes of the digest, big-endian, form the unsigned 64-bit integer H.

Quote Persistence §5.8

Publish a new Target Order Book when any of these change: final bid or ask price; ladder structure; final displayed quantity due to position or configuration change; Market State; Reference Price Version; a Position Version materially affecting price or quantity; applicable public-book constraints; Configuration Version; suspension status.

Never publish solely because: a sweep ran without authoritative change; a duplicate or rejected event arrived; a public-book update left final MM prices unchanged; a different deterministic quantity could exist; a venue acknowledgement confirmed intent; nothing final changed.

Material position change: a Position Version triggers reconstruction, but publication requires the update to move Inventory Adjustment by ≥ $0.005, change any rounded quote price, change any displayed quantity by ≥ 500 shares, or change a permitted side.

Fill Replenishment §5.9

After a partial fill: position updates immediately; remaining quantity stays active; quotes reconstruct; replacement occurs only if the recalculated target differs from the remaining working state.

A level replenishes when remaining quantity falls below 50% of target displayed quantity, after a normal delay of 15 seconds from the latest fill on that order.

Immediate replenishment (no delay) when: the order fully fills; the entire quoted side empties; Market State changes; Reference Price or Position changes enough to alter a quote price; or Recovery Ready requires controlled reconstruction.

Replacement quantity equals the latest Target Order Book quantity — never a restoration of the pre-fill quantity.

A fill always creates a new Position Version; it creates a new Quote Version only when the resulting Target Order Book differs.

Target Order Book Validation (pre-publication) §5.10

All sixteen checks must pass or publication is blocked and a Quote Construction Exception is raised:

  1. Reference Price Status permits quotation
  2. Market State permits quotation
  3. Reference Price within numeric bounds
  4. Position Version authoritative
  5. Public book version valid or expressly unavailable
  6. Every price a valid tick
  7. Every quantity a valid increment
  8. Every quantity within min/max
  9. Bids strictly descending
  10. Asks strictly ascending
  11. Best bid < best ask
  12. No intentional cross of an actionable participant quote
  13. No duplicate same-side price
  14. Boundaries satisfied

  16. Deterministic hash inputs complete

Chapter 06

Market State Engine

States and Inputs §6.1

StateMeaning
StableFull normal quoting
ActiveQuoting with widened, reduced-risk parameters
DefensiveMost restrictive active quoting
SuspendedNo quotation permitted

Market State is per security unless a system-wide condition applies. It is determined only from: Manual Override State, Recovery State, Reference Price Status, Venue Synchronization and Connection States, Security Lifecycle State, and the active Configuration Version. It never depends on position, volume, P&L, sports events, order-book imbalance, or operator discretion.

Determination Precedence §6.2

  1. Manual Kill Switch or Security Suspension
  2. Security Lifecycle State
  3. Recovery State
  4. Reference Price Status
  5. Venue Connection and Synchronization State
  6. Promotion dwell requirements
  7. Normal evaluation

The first condition requiring the most restrictive state controls.

Condition Mapping §6.3

ConditionRequired Market State
Global kill switch activeSuspended (all securities)
Security suspension active / release requested but unapproved / manual recovery activeSuspended
Security Lifecycle in any state other than TradingSuspended
Recovery State: Recovery Required, Restoring, Reconciling, Validating, or FailedSuspended
Recovery State: ReadyDefensive

Venue Connected + DegradedAt least Defensive

Transition Rules §6.4

Demotions are immediate. Whenever the mapping requires a more restrictive state, the transition occurs at once; entering Suspended publishes an empty Target Order Book and initiates cancellation of cancellable orders.

Promotions climb one rung and require dwell. Suspended → Defensive → Active → Stable. Suspended never transitions directly to Active or Stable; Defensive never directly to Stable.

Unchanged conditions publish nothing. A persisting condition creates no new Market State Version.

Promotion Dwell (default 10 seconds each) §6.4.1

Defensive → Active requires, continuously for the dwell: RP Status Valid or Warning; venue Connected; Synchronized or ordinary synchronizing; Recovery Normal or Ready; no suspending override; lifecycle Trading.

Active → Stable requires, continuously for the dwell: RP Status Valid; venue Connected and Synchronized; Recovery Normal; no exception requiring Active/Defensive; lifecycle Trading.

Any condition requiring the current or a stricter state resets the promotion timer to zero. Dwell progress is recorded but creates no new version until the state changes.

Chapter 07

Event Processing, Sequencing & Idempotency

Event Envelope §7.1

Every event submitted for authoritative processing uses one standard envelope: Event ID; Event Type; Event Schema Version; Event Domain; Source ID; Source Message ID; Idempotency Key; Correlation ID; Causation ID; Security ID, Game ID, Competition ID (as applicable); Provider Sequence; Provider Event Time; InPlay Receive Time; Accepted Event Sequence (assigned only on acceptance); Accepted Time; Configuration Version; Payload; Payload Hash; Trace ID; Audit ID.

All authoritative timestamps are UTC, ISO 8601-compatible, with at least millisecond precision; source offsets are preserved for audit. Local time is never authoritative; daylight-saving transitions never alter ordering. Event time, receive time, and processing time remain distinct concepts.

Lifecycle §7.2

  1. Received
  2. Authenticated
  3. Schema Validated
  4. Business Validated
  5. Deduplicated
  6. Sequenced
  7. Accepted
  8. Processed
  9. Published
  10. Audited

A rejected event receives no Accepted Event Sequence but always receives a rejection audit record.

Idempotency §7.3

Event ID identifies one produced record; the Idempotency Key identifies the business occurrence. Two Event IDs may share a key on retransmission; only one business effect is accepted per key within the retention period.

Event typeIdempotency basis
Probability UpdateSource ID + Game ID + Provider Sequence
Official ResultSource ID + Game ID + Result Version
ExecutionVenue ID + Execution ID
Order AcknowledgementVenue ID + Order ID + Acknowledgement Sequence
Configuration ActivationConfiguration Version
Manual ControlControl Action ID
Corporate ActionCorporate Action ID
IPO AllocationIPO ID + Allocation Version
CheckpointCheckpoint ID

Duplicates receive no second Accepted Event Sequence, modify nothing, publish nothing, and generate a Duplicate Event audit record. Conflicting duplicates (same key, different payload) never overwrite the accepted event; they enter exception handling, raise a data-integrity alert, and trigger recovery or suspension when the affected input cannot be trusted. Corrections require a new approved correction identifier or sequence.

Accepted Event Sequence §7.4

One Event Sequencer assigns the Accepted Event Sequence: globally unique, strictly increasing, never reused, durably persisted atomically with the event before business processing begins. Sequence values unused due to pre-acceptance failure are never reassigned; replay processes accepted events in increasing order and ignores documented unused values. Assignment occurs only after authentication, schema validation, business validation, and duplicate determination.

Quote Cycle §7.5

A Quote Cycle is the deterministic process by which one qualifying trigger may produce a new Target Order Book. It consumes exactly one version each of: Reference Price, Market State, Position, Venue State or Public Order Book (as applicable), Configuration, and one triggering Accepted Event Sequence. A Quote Cycle does not necessarily publish; publication follows §5.8. Stale-commit prevention applies throughout: an older calculation never overwrites newer authoritative state.

Chapter 08

Venue Synchronization & Order Lifecycle

Responsibility §8.1

Only the Venue Synchronization Engine communicates with the venue. It converges the venue toward each published Target Order Book by computing the difference between the target and the confirmed venue book and issuing the minimal set of submit, replace, and cancel instructions. The Quote Construction Engine publishes intent; this engine determines implementation. It owns the working book, the confirmed book, order states, pending exposure (§4.4), and Venue Status, and it emits Execution Events to the Position & Execution Engine.

Interface Rules Pending ICD §8.3

Pending the Matching Engine ICD Until the Matching Engine ICD expressly confirms otherwise, Novosapien shall treat every replace as cancel-and-new for queue-priority purposes, and shall not assume priority preservation for quantity-reducing replaces. Instruction timeouts, retry counts and intervals, message-rate limits, and market-data maximum age are OPEN (Chapter 14, items C-4 through C-8) and shall be implemented as configuration with no hard-coded assumptions.

Chapter 09

IPO Allocation & Security Lifecycle

IPO Process §9.1

  1. Configuring
  2. IPO Open
  3. IPO Closed
  4. Allocation
  5. Market Maker Allocation
  6. Treasury Allocation
  7. Reconciliation
  8. Complete

Secondary trading never begins before Complete. After IPO Close, no new orders, cancellations, or quantity modifications are accepted, and queue priority is immutable.

Queue priority: earliest acceptance timestamp, then lowest sequence number, then lowest Order Identifier.

Oversubscribed: allocate strictly by queue priority until all issued shares are assigned; no investor receives more than requested; unfilled demand expires; no proportional allocation in Version 1.

Undersubscribed: investor allocations complete first; the remainder becomes Unsold Shares; completed investor allocations are never modified.

Market Maker and Treasury Allocation §9.2

MMAllocation  =  floor( 0.85 × UnsoldShares )
TreasuryAllocation  =  UnsoldShares − MMAllocation

The Market Maker purchase is automatic, atomic, and at the IPO Price; fractional remainders accrue to Treasury (e.g., 101 unsold → 85 MM, 16 Treasury). Opening Inventory equals exactly the purchased quantity, and the Share Conservation Rule — every issued share has exactly one owner — must hold exactly at all times.

Security Lifecycle States §9.3

Configuring, IPO Open, IPO Closed, Allocating, Pre-Open Ready, Trading, Halted, Settlement Pending, Settled, Extinguished, and Recovery. Only Trading permits Market Maker quotation (§6.3); every other lifecycle state forces Suspended.

Chapter 10

Recovery, Replay & Audit

Recovery States §10.1

StateMeaning
NormalNo recovery activity required
Recovery RequiredIntegrity loss identified; affected quotation suspended
RestoringAuthoritative state being reconstructed from checkpoint plus event replay
ReconcilingReconstructed state compared with external (venue) state
ValidatingRecovered state under deterministic validation
ReadyRecovery succeeded; controlled resumption permitted (transitional only)
FailedRecovery cannot complete without escalation or approved intervention

Recovery Rules §10.2

The path is Recovery Required → Restoring → Reconciling → Validating → Ready; any failure at a stage retries per runbook, falls back one stage, or moves to Failed on exhaustion or unresolvable mismatch.

Ready leads only to Defensive Market State (§6.3); controlled resumption creates a post-recovery checkpoint and returns Recovery State to Normal. Recovery never returns directly to Stable.

Failed never transitions directly to Ready or Normal; only an approved revised recovery plan restarts the process at Recovery Required. Manual alteration of business state is rejected absent a formal amendment.

Recovery cancellation is permitted only before restoration begins and only with independently verified integrity.

Checkpoints and Replay §10.3

Checkpoints capture complete authoritative state with version references and integrity hashes at configured intervals and at recovery boundaries. Replay — reprocessing accepted events in Accepted Event Sequence order from a checkpoint — is the authoritative verification mechanism: it must reproduce identical Reference Price Versions, Market State Versions, Target Order Books, position records, and audit identifiers. Replay equality is a certification gate (§13.2).

Audit §10.4

Every published authoritative object, every accepted and rejected event, every state transition (with reason code), every instruction, and every manual action produces an immutable audit record with a unique Audit ID. Audit records are never modified or deleted within the retention period. The audit retention period is OPEN (Chapter 14, item E-2).

Chapter 11

Challenge Integration, Matching & Settlement

Boundary §11.1

Version 1 operates in the InPlay Challenge simulated environment: simulated shares, simulated cash, no production clearing or broker-dealer records. All shares obey the Share Conservation Rule at all times. The Market Maker uses a distinct system account, receives no preferential queue priority, never internalizes participant orders outside the matching engine, and never submits participant-owned orders.

Matching §11.2

The Challenge Matching Engine matches by strict deterministic price–time priority: better price first (higher for buys, lower for sells); equal prices by earliest priority timestamp. Execution price is always the resting order price, whether the resting order is a participant or the Market Maker. Partial fills are permitted; each execution carries a unique Execution ID, price, quantity, cumulative and remaining quantities, venue sequence, and timestamp. One incoming order may produce multiple executions.

Self-trade prevention: the same participant account never trades against itself; all Market Maker instances share one self-trade-prevention group and never trade against each other. A prevented self-trade creates no execution, position change, P&L, or leaderboard effect.

Final Settlement §11.3

FinalSettlementValue  =  FinalRealizedOnFieldValue + FinalRealizedOffFieldValue

Final settlement follows the final regular-season game and its off-field publication for each security (§2.5); postseason play never affects settlement. At settlement no expected value remains, all results and off-field amounts are final, and Reference Price Status must be Valid. The settlement value carries a Settlement Version, approval record, effective timestamp, source versions, calculation hash, and audit evidence.

ParticipantCashEffect  =  PositionQty × FSV
MarketMakerCashEffect  =  NP × FSV

Long positions receive settlement value; permitted shorts pay the settlement obligation; all positions go to zero, updating cash, realized P&L, Global P&L, and leaderboard source data.

Market Maker settlement enters MM realized P&L and never affects participant prizes except through accepted executions and approved competition metrics.

Treasury shares are extinguished without participant cash, prize, or leaderboard effect (unless Competition Rules require a separate Treasury ledger).

Each security publishes one authoritative Settlement Record: settlement_id, competition_id, security_id, settlement_version, final_trading_cutoff, final_reference_price_version, final on-field and off-field values, final_settlement_value, results and off-field versions, outstanding participant position, MM net position, treasury shares, settlement_status (PENDING / VALIDATING / APPROVED / SETTLED / CORRECTED / FAILED), approval_id, effective_timestamp, calculation_hash, audit_id.

Chapter 13

Golden Tests & Acceptance

Test Authority and Comparison Standard §13.1

Golden Tests are the executable definition of correctness. Each test fixes the initial state, configuration version, and accepted event sequence, and asserts field-level equality of every resulting authoritative object — prices, quantities, versions, states, statuses, and hashes. Approximate comparison is not conformance. Tests are independent, order-insensitive, and runnable in any certified environment.

Mandatory Coverage §13.2

The suite shall cover, at minimum: IPO allocation (including the 85% floor rule and share conservation); valuation (formula, recalculation, publication rule); probability validation, normalization, duplicates, ordering, and corrections; data quality, freshness, status, and confidence; position accounting including average cost, zero-crossing, and P&L; inventory skew including clamps and sign; quote prices including rounding, lock/cross repair, and boundaries; public-book interaction including deviation threshold, one-sided and crossed books; quantities including modifiers and deterministic variation reproducibility; refresh and replenishment timing; Market State mapping, precedence, dwell, and reset; order and instruction lifecycles; event processing, idempotency, conflicting duplicates, and sequencing; venue synchronization and reconciliation; recovery paths including Failed; configuration activation and rollback; Challenge matching, self-trade prevention, and settlement; audit completeness; and performance under the certified load profile.

Replay certification: restore from checkpoint, replay the accepted sequence, and compare every authoritative object for exact equality. Failure-injection: venue disconnects, provider gaps, conflicting duplicates, and process restarts at every pipeline stage must produce the specified degraded or suspended behavior, never invented state.

Acceptance §13.3

Certification requires: every mandatory Golden Test passing; replay certification passing; interface certification against approved ICDs; settlement certification; performance and resilience certification; a complete Requirements Traceability Matrix mapping every section of Chapters 2–13 to code and tests; retained verification evidence; and a written Novosapien conformance statement. Use or testing is not implied acceptance; InPlay retains final acceptance authority. Tests dependent on OPEN items (Chapter 14) remain Draft until the underlying rule is approved, and no Critical requirement may be Blocked at acceptance.
