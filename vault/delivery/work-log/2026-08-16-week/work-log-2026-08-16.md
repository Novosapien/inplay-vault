## The week in one paragraph

InPlay ran its first live NFL preseason games on **13, 14 and 15 August**, three
consecutive nights. Everything else in
this log follows from that. The engines had run against a synthetic feed for weeks. Real
games broke them in ways a synthetic feed never could, and the pattern of the week is the
same in five repositories: a fault appeared on a game night, and it was fixed that night.
The market maker ran a planned programme of six numbered fixes. The Sportradar service
took eight same-night corrections. The FIX gateway filled its disk and lost both venue
sessions for one hour and forty minutes. The app stopped inventing prices. The admin panel
stopped claiming a game was overnight while the engine traded it live. None of this is
new features. It is the week the system met reality.

## The five things that matter

### 1. The engines met real games, and real games won

`inplay-market-maker` · `inplay-sportradar-service` · `inplay-fix-gateway-go`

The market maker's CA/CB fix set is a numbered programme, not a list of unrelated fixes.
It closed the defects the 13 and 14 August games exposed. The engine now keeps a game's
opening price across a restart, refuses to cross a live market, and heals its own orders
at boot. It also processes venue messages about 28 times faster.

The Sportradar service took six correctness fixes to the market-maker publisher alone,
plus post-game polling and cache-lifetime work. It also learned to find live games by
itself instead of waiting for a person to type a game id.

The gateway removed four states in which an order or a price could stay wrong for ever.

### 2. The system stopped stating more than it could prove

`inplay-app` · `inplay-admin-panel-trading`

Both front ends had the same defect in different forms. The app generated a plausible
order book when it had no data. The admin panel printed a confident zero when the engine
was not publishing, and read a stale sports schedule instead of the engine's own account
of what was live.

On 14 August the engine held game-bound books LIVE and filled orders on them, while every
Game chip on the panel read OVERNIGHT. The cause was a flushed Redis cache in the
Sportradar service: two redeploys removed the team map, so the board join returned nothing,
and the absence of the board outranked the presence of the engine. The next night the same
false reading returned for a different reason — the board had recovered, but the cached
regular-season schedule holds no preseason games, so it returned each team's September
opener. A fixture weeks away beat live engine truth.

Both front ends now say what they do not know.

### 3. The market maker starved the retail order feed

`inplay-trading-service` · `inplay-market-maker` · `inplay-app`

Real users saw their own order updates minutes late, because the market maker flooded the
shared event queue. This happened twice. It is the clearest cross-service fault of the
week: a house engine and a retail user competing for one channel, with the user losing.
The app records the same fault from the other side — order pushes ran minutes behind, which
left the trade ticket on a stale side.

Two further problems sat alongside it. Prices on screen ran up to forty minutes behind the
venue, because the market feed committed one message at a time. Users could not buy at the
market price, because the venue accepts limit orders only, so a synthetic market order had
to be built.

### 4. The gateway filled its disk and both venue sessions dropped

`inplay-fix-gateway-go`

On 15 August the gateway VM reached 100% disk. Both FIX sessions went down. The market
maker had no venue connection for about one hour and forty minutes. The team archived the
logs, installed a daily rotation, and wrote the storage rules into the repository so the
same fault cannot repeat unseen.

This is the only unplanned outage in the week's record.

### 5. The written record caught up

`inplay-vault` · `specs`

On 9 August a live probe decoded an undocumented venue rule, and the same day produced two
normative lists of what must be true before the market maker and the taker go live —
`requirements.md` and `market-taker-requirements.md`. Those two documents are the brief the
rest of the week executed against.

The `specs` folder became a git repository for the first time. Twelve written plans now
have a history rather than only a filesystem. The mapping from spec to service is in
[[supporting]]; it is the index to why each service did what it did.

## Open risks

These are carried forward from the service files. Each one is a decision, not a bug.

**`inplay-sportradar-service` `origin/main` is twelve days stale.** Every change from
12 August onward sits on `dev` and `testing` only: live worker discovery and hardening, all
six publisher correctness fixes, cache lifetimes, the whole preseason schedule change, and
the win-probability feed. The gap was deliberate for the 13 August go-live, which ran
entirely in testing. It has not been revisited since.

**Most of the app's week has not reached users.** The no-fabricated-prices work, the
performance fixes and the live-worker reads sit on `prerelease`.

**The market-maker boot healer is inert.** The gateway shipped `GET /orders/mm` — the route
the healer reads — and it is live in gateway `main`. The healer cannot use it because
`MM_GATEWAY_OPS_URL` is unset.

**A gateway deployed without `OPS_API_KEY` breaks the broker.** Mutating ops routes now
require `X-Ops-Key`, and an unset key returns 503 and disables those routes, including the
buying-power call.

**`trader-lite` users reach the leaderboard endpoints.** Non-US users will appear on the
payout board when secondary opens on **27 August**, unless the separate global board ships
first. This is the only dated deadline in the week's record.

**Three trading-service features are dark by default.** Synthetic market orders
(`synth_enabled` false), realized-P&L leaderboard mode (`lb_realized_mode` false), and
referral top-up in the app (flag-gated, and the app's own config file warns that flipping
it before the scheduler exists leaves a user with a top-up nothing credits).

**One observability contract is wrong.** The admin trading spec puts `activity_state` at
the top level as one value for the bot, but the market maker derives it per book. The panel
cannot see which books are live.

**`/sr/winprob` takes no `season_type`,** so preseason ids never reach it. The app fills
the gap client-side, capped at 20 probes, and the workaround retires itself when the
endpoint learns `season_type`. That ask sits with the service team.

## Method

One agent per service read that repository's git history directly: the full commit set for
the window, the diff behind every change described, merge state per branch against that
repository's own mainline branches, and the repository's own documents for the reasons the
commits omit. Nothing was written to any repository.
